## 2. Exact RPC / function names the client calls (new/changed only)

| Client call | Backend object | Type |
|---|---|---|
| `sbClient.functions.invoke('delete-mentor-application', { body: { applicationId } })` | `delete-mentor-application` | Edge Function (**new** — replaces the old `delete_mentor_application` RPC call) |

The old `sbClient.rpc('delete_mentor_application', { p_application_id })` call has been removed from both dashboards. The RPC itself still exists in the database (kept as a safety net) but now only raises an exception directing any caller to the Edge Function above — it can no longer perform a deletion.

## 3. Deploying the frontend

Upload every file in this project (outside `supabase/`) to your static host exactly as-is — same filenames, same relative paths, no build step. If this project is connected to GitHub: **pushing to GitHub does not apply Supabase migrations and does not deploy Edge Functions.** Those live in Supabase, not your static host, and require the separate steps below regardless of whether the GitHub push succeeds.

## 4. Deploying the migration

`supabase/migrations/20260801090000_038_deprecate_direct_storage_delete.sql` is **already applied** to the live `hnmpcjdlhuhetgkzgdgl` project — verified directly against the database as part of this release (its current definition was queried and confirmed to match). No action needed there. Use this section only when setting up a fresh Supabase project from this codebase, in which case every migration under `supabase/migrations/` must be applied in filename order (they're timestamp-prefixed, so alphabetical order is correct order), not just this one.

### Option A — Supabase CLI
```bash
supabase login
supabase link --project-ref hnmpcjdlhuhetgkzgdgl
supabase db push
```

### Option B — SQL Editor (manual, no CLI)
Open Dashboard → SQL Editor, and run each file under `supabase/migrations/` in filename order. On a brand-new project, every earlier migration must run first — later ones (including 038) depend on tables, columns, and functions the earlier ones create.

Verify afterward:
```sql
select pg_get_functiondef(oid) from pg_proc where proname = 'delete_mentor_application';
```
The returned function body should contain the text `raise exception 'Mentor application deletion must go through the delete-mentor-application Edge Function...'` — if it instead contains a `delete from storage.objects` line, migration 038 has not been applied.

## 5. Deploying the Edge Function

`delete-mentor-application` is **already deployed** to `hnmpcjdlhuhetgkzgdgl` (version 1, `ACTIVE` — confirmed directly against the project as part of this release). Use this section only for a fresh project or to redeploy after a further code change.

```bash
supabase login
supabase link --project-ref hnmpcjdlhuhetgkzgdgl
supabase functions deploy delete-mentor-application
```

This is the real, final function slug — not a placeholder. (The project's other functions, unchanged this release, are `delete-user`, `mentor-application-submitted`, `mentor-application-status-changed`, and `orbit-ai`; redeploy those too if standing up a fresh project — see `V20.1-DEPLOYMENT.md` for those commands.)

### Required secrets
```bash
supabase secrets set SUPABASE_URL=https://hnmpcjdlhuhetgkzgdgl.supabase.co
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=<service role key — Dashboard → Project Settings → API — never commit this>
```
These two are provided automatically inside the Supabase Edge Function runtime for functions deployed via the CLI/dashboard against their own project; confirm both are present under Dashboard → Edge Functions → `delete-mentor-application` → Secrets if a manual deploy ever reports them missing. No additional secrets are required by this function — it does not call any third-party service.

### Storage bucket this function depends on
`mentor-applications` (private, not public) — already exists on the live project. The function reads `resume_file_path` and `certs_path` from each `mentor_applications` row and removes exactly those object keys via `storage.from('mentor-applications').remove(filePaths)`. No bucket configuration change was needed or made.
