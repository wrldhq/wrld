# WRLD Website V20.6.1 — Onboarding Test Report

This report is deliberately explicit about what was and was not tested, and against what. Two different real capabilities were available in this environment and both were used:

- **Direct, live, read access to the connected `WRLD-production` Supabase project** (`hnmpcjdlhuhetgkzgdgl`) via schema/data inspection tools — used extensively, described below.
- **No live browser.** `list_connected_browsers` was checked and returned no connected Chrome instance, so no click-through browser test of signup → welcome → assessment → dashboard was possible. Outbound `curl`/network access from the shell sandbox to `*.supabase.co` is also blocked by this environment's network allowlist (confirmed: a direct HTTPS request to the Auth REST API returned a `403 blocked-by-allowlist` from the environment's own proxy), so a fresh synthetic `signUp()` call could not be issued from the shell either. **The database-level evidence below comes from real signups already performed against this project through the actual product** (by you, during V20.6 testing), inspected directly — not from a new call made in this session, and not fabricated or reconstructed from memory.

**Bottom line: the root cause was found and fixed using real, live data from your connected Supabase project. The fix itself (a client-side `localStorage` change) could not be exercised end-to-end in an actual browser in this environment. Do not treat this as a substitute for you clicking through the flow once on the deployed site — see the "What you should still verify" section at the end.**

## 1. Real Supabase signup response — Case A and Case B

### Method
Live inspection of `auth.users` for the connected project (`execute_sql`, read-only), cross-referenced against the `handle_new_user()` trigger's actual source (read directly from `pg_proc`, not assumed).

### Case A: immediate session (the live, active configuration)

Confirmed directly from real account rows — for both existing accounts in the project:

| | `hello@ourwrld.org` (Owner) | `test@gmail.com` (Explorer, created during V20.6 testing) |
|---|---|---|
| `confirmation_sent_at` | 2026-07-26 16:26:59 (an email *was* sent — see note) | **`null` — no confirmation email sent** |
| `confirmed_at` | 2026-07-26 16:27:24 (25s after signup — a real click) | **2026-07-28 14:40:02.076 — same second as `created_at`** |
| `last_sign_in_at` | 2026-07-28 14:38:58 | **2026-07-28 14:40:02.093 — same second as `created_at`** |

The `test@gmail.com` row is unambiguous: `confirmed_at` and `last_sign_in_at` both land in the same second as `created_at`, with no `confirmation_sent_at` at all. This is only possible if Supabase's `signUp()` call returned an active session immediately, with no email round-trip — i.e., **Case A (`data.user` exists, `data.session` exists) is the live, current behavior of this project**, consistent with "Confirm email" being off, as documented in `CLAUDE.md`. (The Owner account's older `confirmation_sent_at`/25-second gap to `confirmed_at` reflects an earlier point before or during setup — not the current signup path new users go through today.)

### Case B: email confirmation required

Not currently reachable on this project (per the evidence above), so it could not be exercised live. The code path (`needsEmailConfirmation` branch in `signUp()`, `check-your-email.html`, `email-verified.html`) was inspected in V20.6 and confirmed to route through the same shared `postAuthDestination()` onboarding check if this setting is ever turned back on — unchanged in V20.6.1, since this release's bug and fix are both entirely in Case A's local-progress-caching path.

## 2. Onboarding source of truth — traced against the live schema

### Method
`list_tables` (verbose, public schema) and a targeted `information_schema.columns` search across every `public` table for `%onboard%`/`%assessment%`.

### Result

Exactly one matching column exists anywhere in the live schema: **`public.learner_state.assessment`** (`jsonb`, nullable, no default). No `onboarding_completed` column, no separate onboarding table, and no profile-metadata flag exists — confirming `getState().assessment` (client) / `learner_state.assessment` (server) is genuinely the only persistent onboarding signal in this project, exactly as `auth.js`'s `needsOnboarding()` already assumes.

### The value created for a brand-new profile

Read directly from the live `handle_new_user()` trigger function source:

```sql
insert into public.profiles (id, name, email, email_verified)
values (new.id, coalesce(new.raw_user_meta_data->>'name', split_part(new.email,'@',1)), new.email, new.email_confirmed_at is not null);
```

This trigger **only** inserts into `public.profiles`. It never inserts a row into `learner_state`. A genuinely brand-new account therefore has **no `learner_state` row at all** immediately after signup — confirmed by the row count and the trigger source together, not assumed. `needsOnboarding()`'s query (`select * from learner_state where user_id = :id`) correctly returns nothing for such an account, and correctly resolves `needsOnboarding()` to `true` — provided nothing else writes a foreign row into `learner_state` first. That "provided" is exactly where the real bug was (see `CHANGES-V20.6.1.md`).

### The exact query used after login

`pullLearnerStateFromSupabase()` (`app.js`), called automatically inside `wrldRefreshSessionCache()` (`supabase-client.js`) right after every login/signup/session-restore:

```js
sbClient.from('learner_state').select('*').eq('user_id', user.id).maybeSingle()
```

Confirmed correct — right table, right column, right filter. The bug was never in this query; it was in what happened next when this query legitimately (and correctly) returned no row for a brand-new account.

## 3. Direct evidence of the live bug

Already documented in full in `CHANGES-V20.6.1.md` — summarized here: a real `test@gmail.com` Explorer account, created live in the connected project during V20.6 testing, had a `learner_state` row appear one second after its own creation, containing an Adulting Readiness Assessment result with a completion timestamp from two days before the account existed — identical to the Owner account that had been signed into the same browser about a minute earlier. This is the actual, live reproduction of the reported bug, inspected directly from the database rather than inferred.

**What could not be tested in this environment:** any step requiring an actual browser session — clicking through signup, watching the welcome/Orbit screen render, taking the assessment UI, and observing the final dashboard redirect. **What was tested against the real, connected project:** the actual schema, the actual trigger function source, the actual signup response behavior (via existing real account rows, not a fabricated test), and the actual, live root-cause data (the corrupted `learner_state` row) that proves the bug and confirms the fix targets the right mechanism.

## What you should still verify

Because no browser was available here, please do one real end-to-end pass yourself after deploying this release, exactly as the original request specified:

1. On a browser/profile that has **previously been signed into any other WRLD account** (this is the scenario that reproduced the bug), sign up with a brand-new, unique email.
2. Confirm you land on the Welcome/Orbit page, not the dashboard.
3. Complete the assessment and confirm you reach the Explorer Dashboard afterward.
4. Sign out, sign back in, and confirm you go straight to the dashboard (not onboarding again).

If step 2 still fails after deploying this fix, the most likely next thing to check is whether the deployed `app.js` is actually the updated one (browser cache / CDN cache of the old file) rather than a further code defect — worth ruling out first.
