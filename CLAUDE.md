Before making **any** change, do all of the following, in order:

1. **Read this entire file first.** It describes the real, current state of the codebase — don't assume anything about WRLD from general web-project conventions.
2. **List the folder and open the actual files you're about to touch** before editing them. This project has gone through many iterative phases; the file on disk is the only reliable source of truth, not this document's prose descriptions of it (though this doc is kept accurate — see the maintenance rule at the bottom).
3. **Never rebuild a page, file, or feature from scratch** if it already exists and works. WRLD is a mature, working platform, not a prototype. Read the existing implementation and extend or edit it surgically. If you think something needs a full rewrite, say so and explain why before doing it.
4. **Preserve every existing working feature.** Authentication, the Owner/Moderator dashboards, the Volunteer Tracker, Community moderation, the Assessment, Orbit, and all 23 Playbooks are fully built and functional. Don't remove, simplify, or "clean up" any of this unless the user explicitly asks.
5. **Match the existing conventions exactly** — see "Naming & Coding Conventions" below. New code that doesn't match the established patterns (localStorage-store shape, `initPage()` usage, `.pb-card`/`.card`/`.pill` class system, script load order) will look and behave inconsistently with the rest of the site.
6. **Verify before you say you're done.** At minimum: `node --check` every `.js` file and every inline `<script>` block you touched, confirm no broken local `href`/`src` links, and confirm no leftover placeholder/lorem-ipsum/TODO language. This project has a strong "never fabricate content or features" ethic — see below.
7. **Update this file** (the "Maintaining This File" section at the bottom has the rule) whenever you make a meaningful change — new page, new data store, new dashboard section, changed account flow, etc.

If the user's request is ambiguous about which existing page/section it affects, open the relevant files and confirm before guessing.

## What WRLD Is

WRLD ("the curriculum for adulthood") is a free educational platform teaching practical life skills school doesn't cover — resumes, budgeting, credit, taxes, apartment hunting, mental wellness, and more — through long-form guided lessons called **Playbooks**, sequenced **Learning Paths**, live **Programs**, downloadable **worksheets**, an AI-personalized **Assessment**, a **Community** with real moderation, a **Volunteer Hours Tracker**, and a full **account/role system** with Explorer, Mentor, Administrator, and Owner tiers.

The founder is Desiree Yhap (see `about.html`). The brand is warm, honest, and explicitly non-corporate — copy throughout the codebase actively avoids sounding like generic SaaS marketing, and the project has a strong, repeated internal rule: **never invent content, stats, testimonials, or features that don't exist.** Anything not yet built is labeled "Coming Soon" confidently rather than faked.

## Current Architecture (Read This Before Assuming Anything)

**WRLD is a 100% static frontend — HTML, CSS, and vanilla JavaScript, no build step, no bundler, no framework.** There is no Node/React/Vue anywhere in this codebase; every file is opened directly by the browser. As of the V13 revision ("Revision Pass 12," Priority 3), it is backed by a **real Supabase project** (Postgres + Auth + Storage) instead of `localStorage` for accounts — see "Authentication & Backend (Supabase)" below. This is still not a build-step app: Supabase is reached directly from the browser via the Supabase JS SDK (loaded from a CDN `<script>` tag) and Row Level Security, the same way any other static-HTML site would call a REST API.

**What moved to Supabase (real, persistent, cross-device):**
- Accounts, login sessions, and user profiles (`auth.js` + `supabase-client.js`, backed by `auth.users` + `public.profiles`).
- **Learner progress** (`wrld_state_v1` / `getState()`/`setState()`) — bookmarks, completed Playbooks, streak, quiz scores, checklists, recently-viewed, assessment results. Synced to `public.learner_state`.
- **Volunteer log** (`wrld_volunteer_log_v1` / `getVolunteerEntries()`/`saveVolunteerEntries()`) — every logged entry plus its verification heuristic result. Synced to `public.volunteer_entries`.

Both of the above use the **same write-through-cache pattern as auth**: `setState()`/`saveVolunteerEntries()` still write to `localStorage` *synchronously* first (zero behavior change for the dozens of existing call sites that call them inline from click handlers with no `await`), then fire an un-awaited background upsert to Supabase. On the *read* side, `pullLearnerStateFromSupabase()`/`pullVolunteerEntriesFromSupabase()` (both in `app.js`) run automatically, once per session, from inside `supabase-client.js`'s `wrldRefreshSessionCache()` — meaning **every page gets this sync for free** via the existing `await window.wrldAuthReady` plumbing, with zero additional per-page wiring. If the account already has server-side data (e.g. from another device), it overwrites the local cache; if not (first sync), whatever's already local gets pushed up. **If you add a new field to the learner state or a volunteer entry, update both the mapping functions (`volunteerEntryToRow`/`volunteerRowToEntry` in `app.js`) and, if it's a genuinely new field, the table via a migration** — don't let the local shape and the DB shape drift apart silently.

**What is still `localStorage`-only (per-browser, not yet synced):** community posts/moderation/reports/trust, mentor applications/profiles, live sessions, announcements, feature toggles, featured picks — all still read/written through `app.js`'s `getX()/setX()` functions exactly as before. **Matching Postgres tables + RLS policies already exist for all of these** (see `supabase/migrations/003`–`005`) — wiring them up follows the same write-through pattern established above, it just hasn't been done yet. Don't assume community posts or mentor profiles sync across devices; they don't yet.

**This means, today:** progress/community/volunteer data is still per-browser and per-device (clearing browser storage still deletes it), there is still no real file upload storage for mentor-application attachments (metadata only), and Owner Dashboard tabs that read those stores (Volunteer, Community, Content) still reflect "this browser's local data" — but the Users/Members tab, and every account action (suspend/ban/promote/reset password), are real and now apply platform-wide. The codebase is honest about this split in its own UI copy — preserve that honesty in any new copy you write, and don't claim a store is synced across devices until it's actually been migrated to Supabase.

## Naming & Coding Conventions

- **No framework, no bundler, no `import`/`export` (ES modules).** Everything is global-scope script tags loaded in a fixed order. New JS must follow this pattern — don't introduce a module system partway through.
- **Every page's inline script ends with a call to `initPage(activeKey, customGuideMessage?)`** (from `app.js`) — this renders the shared header/footer, wires up the mobile menu, sets Orbit's contextual line, and starts scroll-reveal animations. `activeKey` matches a `NAV_GROUPS` item key from `data.js` (or `null` if the page isn't in top nav).
- **All persistent data goes through a `getX()`/`saveX()` or `getX()`/`setX()` pair** wrapping a single `localStorage` key, following the exact pattern of `getState()`/`setState()` in `app.js`. Never call `localStorage` directly from a page's inline script — always go through the shared accessor so the "swap for a real API later" architecture stays intact.
- **Route guards** (`requireAuth()`, `requireRole(roles)`, `requireMinRole(role)` in `auth.js`) are called at the very top of a gated page's inline script, before any rendering.
- **Role checks** use `hasPermission(user, 'permission_name')` or `roleAtLeast(user, ROLES.X)` — never compare `user.role === 'admin'` directly in new code; use the helpers so the Owner (who should pass every Admin check too) isn't accidentally excluded.
- **IDs and localStorage keys are prefixed `wrld_`** and versioned (`_v1` suffix) — see the full list under "Data Model" below. Follow this pattern for any new store.
- **Playbook `slug`s are kebab-case and permanent** — they're the join key across `data.js`, `illustrations.js` (`heroIllustration`), `RELATED_PLAYBOOKS`, `LEARNING_PATHS.steps`, `SECTION_RECS`, bookmarks/completed arrays in learner state, URL query strings (`playbook.html?slug=...`), **and now `images/playbooks/<slug>-card.jpg` / `<slug>-hero.jpg` filenames directly**. Never rename an existing slug without updating every one of those references (including re-exporting/renaming the two image files).
- **No emojis in copy unless matching existing tone** — WRLD's existing copy uses emoji sparingly and purposefully (section eyebrows, pillar icons, milestone badges) — check existing pages for the pattern before adding more.
- **Honesty rule (important, repeated throughout the codebase in comments):** never fabricate testimonials, user counts, activity, or "coming soon" features presented as live. If something isn't real yet, either build it for real or label it "Coming Soon" the way `LEARNING_PATHS_COMING_SOON`, `COMMUNITY_FEATURES` (`status:'coming-soon'`), and the Owner Dashboard's Certificates card already do.

## Account System & Roles

Full implementation in `auth.js` + `supabase-client.js`, backed by real Supabase Auth + `public.profiles`. Four roles, strict hierarchy (each inherits everything below it): **Explorer → Mentor → Admin → Owner**. (The Postgres enum and every JS/CSS reference use the short label `admin`, not `administrator` — see `supabase/migrations/010`/`011` if you're ever tempted to "fix" this back to the longer word; don't, it'll break the enum/CSS/RBAC match.)

- **Capability-based route guards (V14).** Route guards no longer use exact-role-list matching (`requireRole([ROLES.MENTOR, ROLES.ADMIN])`) — that pattern silently excluded the Owner from anything not listing `'owner'` explicitly, which was the root cause of a real reported bug (Owner selecting Mentor Studio was redirected to the Explorer Dashboard). Every gated page now calls `requireCapability(canAccessX)`, where each `canAccessX(user)` (`canAccessExplorerDashboard`, `canAccessMentorStudio`, `canAccessModerationDashboard`, `canAccessOwnerDashboard`, `canAccessAdministratorsPanel`, `canAccessSecurityPanel` — all in `auth.js`) is built on `roleAtLeast()`, so higher roles automatically inherit access to everything below them with no per-role special-casing. **When adding a new gated page or experience, define one new `canAccessX(user)` function this way and call `requireCapability(canAccessX)` at the top of its inline script — never a fresh `requireRole([...])` exact-match list.** Full model, including the Owner's cross-dashboard "master keyring" behavior, documented in `AUTH-SECURITY-SETUP.md`.
- **The Owner has real, secured access to every experience below it** (My Explorer Dashboard, Mentor Studio, Owner Command Centre) via a dashboard switcher in the profile menu (`app.js`'s `loggedInNavCTA()`), without ever changing `profiles.role` away from `'owner'` and without requiring a Mentor application. The Owner is not auto-listed in the public Mentor directory — `get_mentor_directory()` (migration `027`) only shows Admin/Owner accounts that have explicitly saved a `mentor_profiles` row.
- **Public sign-up (`signup.html`) only ever creates Explorer accounts.** `signUp()` calls `sbClient.auth.signUp()`; the `handle_new_user()` Postgres trigger (migration `001`) inserts the matching `profiles` row with `role='explorer'` hardcoded at the database level — there is no role param `signUp()` even accepts, so this is enforced twice, not just in the UI. `signUp()` now also passes an explicit `emailRedirectTo` (built from `wrldSiteUrl()` in `supabase-client.js`) so confirmation links land on `email-verified.html` in production, never a stale/localhost Supabase Site URL default — see `SUPABASE-REDIRECT-SETUP.md`.
- **Becoming a Mentor** happens exactly one way: a real application via `become-mentor.html` (now requires login, uploads real files to the `mentor-applications` storage bucket, and calls the `submit_mentor_application` RPC) → stored in **`public.mentor_applications`** (real Postgres table as of V14 — migration `032` wired up the pre-existing-but-unused table; no longer `wrld_mentor_applications_v1` localStorage) → reviewed by an Administrator/Owner in the Owner Dashboard's Mentors tab (fully rewritten, real search/filter/sort/status-history/internal-notes/signed-document-access) → `set_mentor_application_status(id, 'approved', note)` RPC promotes the applicant's `profiles.role` to Mentor server-side. There is no self-service Mentor signup. See `EMAIL-AUTOMATION-SETUP.md` for the two Edge Functions that send the owner-notification and applicant emails this workflow now triggers automatically.
- **Becoming an Administrator** happens exactly one way: an existing Owner/Administrator promotes an existing account from the Owner Dashboard's Administrators tab (Owner-only panel, `setAdministratorStatus()`). Never selectable at signup, never self-service.
- **The Owner role exists exactly once, forever** — enforced by a partial unique index in Postgres (`profiles`, `where role='owner'`), so it's impossible even for a bug to create zero or two Owners. **Owner bootstrap is real, backend-driven self-service, not a client-side flag**: sign up/log in normally, then visit `owner-setup.html`, which checks real backend state (`public.owner_exists()`) and shows a "Claim Owner Access" button only if no Owner exists yet (`ownerAccountExists()`/`claimOwnerRole()` in `auth.js`). What actually enforces "only once, only while unclaimed" is a database trigger (`guard_profile_updates()`, migration `016`) — never trust the client-side check alone; the trigger is what makes this safe even against a malicious direct API call. A manual SQL alternative (`update profiles set role='owner' where id=...` in the Supabase SQL editor) still works too and is documented in `SUPABASE_SETUP.md`, for anyone who'd rather not leave a public self-claim window open before restricting signups. Ownership can be transferred to an existing Administrator via `transferOwnership()` (Owner-only, demotes the previous Owner to Administrator in the same operation).
- **`profiles` UPDATE is column-guarded, not just row-guarded.** RLS alone only controls which *rows* a user can touch (their own, or any row if admin+) — it does not stop a user from changing *which columns* on their own row, so without the `guard_profile_updates()` trigger, any signed-in Explorer could have called `update profiles set role='admin'` (or un-suspended/un-banned themselves) directly via the client SDK. The trigger blocks any self-change to `role`/`suspended`/`deactivated`/`banned`/`warnings`/`violations` unless the caller is already admin+, with the single carved-out exception of the first-owner claim above. If you ever add a new sensitive column to `profiles`, add it to this trigger's guarded list too — don't assume RLS alone protects it.
- **Login (`login.html`) is a single unified page for every role** — there is no separate Owner or Administrator login screen. After login, routing to the right destination is the calling page's responsibility.
- **Duplicate-email signup** shows a friendly "An account with this email already exists" message (Supabase's own `already registered` error, translated via `friendlyAuthError()`) with direct paths to Log In / Forgot Password — never a raw error, never a duplicate account.
- **Passwords** are handled entirely by Supabase Auth now — hashed and stored server-side, never touched or stored by WRLD's own code. This is real production-grade auth (unlike the old client-side SHA-256-in-localStorage scaffolding it replaced).
- **Email verification** is real — Supabase sends a confirmation email on signup; `signUp()` returns `{ok:true, user:null, needsEmailConfirmation:true}` when a session isn't issued yet, and `signup.html` should show a "check your inbox" state for that case (confirm this is wired before assuming it is).
- **Password reset** (`forgot-password.html` → `reset-password.html`) is now a real email, sent by Supabase Auth (`requestPasswordReset()` → `sbClient.auth.resetPasswordForEmail()`) — no more copy-the-link-yourself UI. Configure the redirect URL and email template in the Supabase dashboard (Authentication → URL Configuration / Email Templates) — see `SUPABASE_SETUP.md`.
- **Sessions**: persistent by default (30-day-plus, auto-refreshing via `autoRefreshToken:true`), with a real **Remember Me** implementation — `wrldAuthStorage` in `supabase-client.js` reads a `wrld_remember_me` flag (set by `logIn()`) to choose `localStorage` (survives browser close) vs `sessionStorage` (cleared on tab close) for the session token.
- **The sync/async bridge**: `getCurrentUser()` must stay synchronous (dozens of existing call sites across 28 pages read it directly, mid-render), but Supabase session lookups are inherently async. `supabase-client.js` resolves the session + profile once into an in-memory cache and exposes `window.wrldAuthReady` (a Promise). `app.js`'s `initPage()` is now `async` and `await`s this before rendering the header; every route-guarded page's inline script is wrapped in `(async()=>{ await window.wrldAuthReady; if(requireAuth()){ ...unchanged... } })();`, and any other top-level code that reads `getCurrentUser()`/`roleAtLeast()`/etc. outside of `initPage()` (e.g. `dashboard.html`'s greeting, `playbook.html`'s discussion gate, `community.html`'s posting gate) is likewise wrapped to await readiness first. **If you add new code that reads `getCurrentUser()` at the top level of a page's inline script, wrap it the same way** — reading the cache before it resolves silently returns `null` even for a logged-in user.
- **Moderation account actions** available to Administrators/Owner: `suspendUser`/`unsuspendUser` (conduct-based, tied to the moderation system), `deactivateUser`/`reactivateUser` (administrative closure, distinct from suspension), `banUser`/`unbanUser` (escalation past suspend, also sets `suspended`). All are now real `async` Supabase writes to `profiles` — every call site in `owner-dashboard.html`/`moderation-dashboard.html` awaits them and calls `refreshUsersCache()` before re-rendering (see `getUsers()`/`refreshUsersCache()` below).
- **`deleteOrganizationData()`** — Owner-only, irreversible, now truncates every WRLD Postgres table (community, volunteer, mentor, announcements, learner_state) rather than wiping `localStorage` keys. Auth accounts themselves are deliberately left alone (a separate, even more irreversible action, done from the Supabase dashboard, not a single in-app button).
- **`getUsers()`/`refreshUsersCache()`** (new, `auth.js`) — the real-user-list equivalent of the old synchronous localStorage `getUsers()`. Backed by `select * from profiles` (Administrator+ only, per RLS), which is async, so it follows the same cache-then-sync-read pattern as `getCurrentUser()`: call `await refreshUsersCache()` once before first render (and again after any action that changes a user row), then read the list synchronously via `getUsers()` mid-render. Owner/Moderator Dashboards already do this.
- **Owner Dashboard → Users → "View Progress"** (`odViewProgress()` in `owner-dashboard.html`) — a real per-user drill-down (Playbooks completed, bookmarks, streak, volunteer hours, verified volunteer entries, whether they've taken the Assessment), reading directly from `learner_state`/`volunteer_entries` for that user's `id`. Toggles open/closed inline on the user row rather than a modal — WRLD has no modal system elsewhere in the codebase, so this matches the existing show/hide convention instead of introducing a new UI pattern.
- **Account "deletion" is deliberately NOT implemented as a hard delete.** Deleting a real Supabase Auth user requires the Admin API (`service_role` key) — which, per the explicit, repeated security constraint in this project, must never be called from client-side code. `deactivateUser()`/`reactivateUser()` (already wired to the Owner Dashboard's "🗑️ Deactivate" button) is the real, safe equivalent available from the browser: it revokes the account's practical access without touching `auth.users`. If a true hard-delete is ever required, it needs a small server-side function (e.g. a Supabase Edge Function that calls `supabase.auth.admin.deleteUser()` using the service_role key from its own server environment, invoked by an authenticated Owner-only RPC) — not yet built, and shouldn't be built by adding the service_role key to any file in this repo.

Added because `community.html`'s public Mentor directory can no longer do a plain `profiles` select-all after migration `012` tightened that RLS policy. If you add another feature that needs to show *some* fields from *other users'* profiles to non-Administrators, follow this pattern (a narrow `security definer` function) rather than loosening `profiles`' own SELECT policy again.
- **Storage buckets**: `avatars` (public), `mentor-applications` (private), `volunteer-proof` (private), all path-scoped RLS (migration `006`) — not yet wired into any upload flow in the HTML/JS (`become-mentor.html`'s resume upload and `volunteer-tracker.html`'s proof upload still only capture file *metadata*, same as before).
- **Security posture**: only the publishable/anon key is ever committed (`supabase-config.js`) — it's safe by design, every request through it is still constrained by RLS. **The service_role/secret key must never appear anywhere in this repo or client-side code.** If a future feature genuinely needs privileged server-side access (bypassing RLS), it belongs in a real server environment (e.g. a Cloudflare Pages Function's environment variable), configured in that platform's dashboard, never committed.
- **Advisors**: run `get_advisors(security)` / `get_advisors(performance)` after any schema change and treat WARN/ERROR-level results as things to fix before moving on — this caught the `profiles` over-broad SELECT policy, several missing FK indexes, and per-row `auth.uid()` re-evaluation in RLS policies during this pass.
- **A revoked EXECUTE grant silently broke every admin RLS check for real users (migration `007` → fixed by `017`).** Migration `007` revoked `authenticated`'s EXECUTE on `role_at_least()` to stop it being called as a public RPC endpoint — but Postgres checks EXECUTE privilege on a `SECURITY DEFINER` function against the actual invoking role even when the call happens from inside an RLS policy expression or a trigger, not just on direct calls. That revoke therefore silently broke every policy that calls `role_at_least('admin')` — which is most of them — for real logged-in users, while every `execute_sql`-based test during development kept passing because those ran as the privileged service connection, never as a simulated `authenticated` session. **This was only caught by simulating a real authenticated session directly in SQL** (`set local role authenticated; set local request.jwt.claims = '...'`) — `get_advisors` doesn't catch this class of bug, and testing via the service-role connection doesn't either. If you ever revoke EXECUTE on a function that any RLS policy or trigger depends on, re-grant it to the roles those policies apply to (`authenticated`, and/or `anon`), and verify with a simulated-session test, not just a service-role one.

## Community & Moderation System

Multi-layer, all real (not simulated), implemented in `app.js`:

1. **Gating** — `canParticipateInCommunity(user)`/`communityGateReason(user)`: posting requires an account and completing at least one Playbook (never anonymous, never open to brand-new signups).
2. **Guidelines acceptance** — `hasAcceptedGuidelines()`/`acceptGuidelines()`, a modal gate (`openGuidelinesModal()`) before first post.
3. **Automated content screening** — `moderateContent(text)`: pattern-matches against categories `selfHarm`, `violence`, `graphicViolence`, `harassment`, `bullying`, `hateSpeech`, `explicitContent`, `dangerousAdvice`, `scam`, `phishing`, `selfPromotion`, plus `personal-info`/`external-link` flags for email/phone/URL, plus a small keyword layer (`flagged-language`). The most severe categories (`self-harm`, `violence`, `graphic-violence`, `dangerous-advice`, `explicit-content`, `hate-speech`) **block outright**; anything else with flags is **held** for human review; clean content is **approved** automatically. Explicitly documented as rule-based pattern matching, not a real ML/AI model — don't claim otherwise in UI copy.
4. **Repeat-offender escalation** — `recordViolationAndMaybeEscalate()`: 3 held/blocked posts from one account auto-suspends it (`VIOLATION_SUSPEND_THRESHOLD = 3`), logged either way.
5. **Progressive trust** — `getTrustState()`/`trustLevel()`/`canPostToday()`: new members get modest daily post/reply limits that grow with real approved participation history.
6. **Reporting** — any user can report a post/reply (`reportCommunityItem()`, `REPORT_HOLD_THRESHOLD = 3` reports auto-hides pending review); Administrators clear or set status (`moderationSetStatus()`) via `moderationClearReports()`.
7. **Full audit log** — `logModerationEvent()`/`getModerationLog()`, every action (auto or manual) recorded with target and flags, visible in Owner/Moderator Dashboards.

**This system covers Community Commons posts (`wrld_community_posts_v1`, still localStorage — see Current Architecture). Playbook-level discussion is a separate, Supabase-backed system as of V14 — see below.**

## Important Decisions & Rationale (Don't Silently Reverse These)

- **Static site, localStorage-first architecture** was a deliberate choice to build the full product experience and information architecture before investing in backend infrastructure — every store function is written to make that migration a drop-in replacement later. **Accounts/auth have now made that swap** (real Supabase backend); the remaining stores are next.
- **Explorer-only public registration; Mentor/Admin are never self-service** — a trust and safety decision, not an oversight. Still true and now enforced twice (UI + database trigger).
- **Exactly one Owner account, now enforced by a database constraint, not a client-side bootstrap trick.** Owner creation is a one-time manual SQL step (see "Authentication & Backend (Supabase)") rather than an automatic passwordless account WRLD's own JS creates on page load — deliberately moved server-side so it can't be spoofed or recreated from the browser.
- **Single unified login page for all roles** — no separate "admin login" that would advertise privileged-account existence.
- **Publishable/anon key committed, service_role key never touched.** The Supabase publishable key in `supabase-config.js` is safe to commit by design (RLS-constrained); the service_role/secret key must never appear in this repo or any client-side code — a repeated, explicit constraint through this entire revision, not a one-off preference.
- **"Coming Soon" instead of fake data** — a recurring, explicit product principle across Learning Paths, Community features, and Certificates. Do not populate these with invented content to make them "look done."
- **Volunteer directory links to real third-party platforms** rather than fabricating WRLD-run opportunities WRLD doesn't actually operate.
- **Orbit and the moderation/verification systems are rule-based, not real AI**, but are product-framed with AI-adjacent language ("AI-assisted verification," etc.) — keep this framing honest in any new copy: describe *what it actually does*, don't claim a model that isn't there.
- **Hero illustrations render at each image's own native aspect ratio, never a forced/uniform one.** The 23 custom Hero images aren't all the same shape (3:2, 4:3, 16:9 all appear). The deliberate call was to show every image in full, uncropped, rather than force visual uniformity across Playbook pages — a one-off size difference between two Playbooks is preferable to cropping an artist's work. Card images, by contrast, *are* uniform 16:9 (that's how they were supplied), so `.pb-thumb` does use a fixed `aspect-ratio:16/9`.
