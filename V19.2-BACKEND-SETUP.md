# V19.2-BACKEND-SETUP.md

This document exists because uploading V19.2 to GitHub does **not**
activate anything below. Every item here requires a real action against
your actual Supabase project.

## 1. Which migration files must be applied

Apply, in order, everything under `supabase/migrations/` that isn't
already applied to your project. For V19.2 specifically, the new file is:

```
supabase/migrations/20260730080000_036_community_tables_and_deletion_repair.sql
```

This migration:
- Re-declares `public.delete_mentor_application(p_application_id uuid)`
  (safe — `create or replace`, doesn't touch existing applications) and
  ends with `notify pgrst, 'reload schema';` so PostgREST recognizes it
  immediately, even if applied via a direct SQL Editor paste rather than
  the CLI.
- Creates `public.community_posts` and `public.community_replies` (brand
  new tables — no existing data touched), with full RLS.
- Creates `public.moderation_set_community_status()` and
  `public.report_community_content()`.

**Apply it with:**

```bash
supabase db push
```

**Or**, if you're not using the CLI: open the Supabase Dashboard → SQL
Editor → paste the full contents of that `.sql` file → Run.

### How to verify the migration actually took effect

Run this in the SQL Editor:

```sql
select proname from pg_proc where proname in
  ('delete_mentor_application', 'moderation_set_community_status', 'report_community_content');

select table_name from information_schema.tables
  where table_schema='public' and table_name in ('community_posts','community_replies');
```

You should see all three function names and both table names. If you
don't, the migration was not actually applied — re-run step above.

If PostgREST still reports "function not found" after confirming the
function exists in `pg_proc`, manually force a schema reload:
Dashboard → **Settings → API → "Reload schema"** button (or wait ~60
seconds; PostgREST also polls for changes automatically on most plans).

## 2. Which Edge Functions must be deployed

```bash
supabase functions deploy delete-user
```

The client calls this exact name —
`sbClient.functions.invoke('delete-user', ...)` in `owner-dashboard.html`
— and the deployed function must live at
`supabase/functions/delete-user/index.ts` (it does, in this ZIP). These
three must always match exactly; if you ever rename one, rename all
three together.

No other Edge Function changed in this pass. `orbit-ai`,
`mentor-application-submitted`, and `mentor-application-status-changed`
are unchanged from V18/V19 and don't need redeploying because of V19.2
(redeploy them only if you're setting them up for the first time — see
`ORBIT-AI-SETUP.md` / `EMAIL-AUTOMATION-SETUP.md`).

### How to verify the function is actually deployed

```bash
supabase functions list
```

Confirm `delete-user` appears with a recent deploy timestamp. You can
also check the Dashboard → **Edge Functions** tab directly.

If `owner-dashboard.html`'s Delete User button still shows "The secure
deletion service is not currently available..." after this, check:
- The function actually deployed without a build error (`supabase
  functions deploy delete-user` should print success, not an error)
- `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` secrets are set (below)
- You're testing against the same Supabase project the site's
  `supabase-config.js` actually points to

## 3. Required secrets

```text
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=
```

These are the same two secrets already required by every other Edge
Function in this project (`mentor-application-submitted`, `orbit-ai`) —
no new secret was introduced for `delete-user`. Set them once, shared
across all functions:

```bash
supabase secrets set SUPABASE_URL=https://<your-project-ref>.supabase.co SUPABASE_SERVICE_ROLE_KEY=<your-service-role-key>
```

**Never commit the real value of `SUPABASE_SERVICE_ROLE_KEY` anywhere in
this repository, any frontend file, or version control.** It lives only
in Edge Function secrets. This ZIP contains no real secret values.

## 4. Which Supabase project must receive the deployment

Whichever project your site's `supabase-config.js` (`WRLD_SUPABASE_URL`)

## 5. How to test public Community visibility

1. Log in as User A, post something in Community Commons.
2. Log out entirely (or open a private/incognito window with no
   session).
3. Load `community.html` again. You should see User A's post — this
   confirms the anon-key RLS policy (`community_posts_select_public`)
   is working.
4. Log in as a different User B (or on a different device/browser).
   Confirm the same post is visible there too — this confirms it's a
   real shared table, not per-browser `localStorage`.
5. Refresh the page. The post should still be there (this sounds
   obvious, but it's the exact symptom that was broken before V19.2 —
   confirm it explicitly).

## 6. How to test author-deletion permissions

1. As User A, post something, then delete it via the "⋯ Delete" control
   on your own post. It should disappear immediately and stay gone after
   a refresh.
2. As User B, confirm you do **not** see a delete control on User A's
   posts (if User B isn't an Administrator/Owner).
3. Attempt a direct RPC/table call as User B trying to delete User A's
   post (e.g., via the browser console: `sbClient.from('community_posts').delete().eq('id','<A's post id>')`)
   — this should silently affect zero rows (RLS blocks it), not error
   loudly, per how Postgres RLS DELETE policies work.

## 7. How to test Owner and Administrator moderation

1. As an Administrator, open the Administrator Dashboard's Community &
   Content Moderation tab (or the Moderator Dashboard) and confirm you
   can Approve/Remove any user's held or reported post — this exercises
   `moderation_set_community_status()`'s Administrator+ check.
2. As an Explorer or Mentor, confirm the moderation controls aren't
   available (they only render in the Owner Command Centre /
   Administrator Dashboard / Moderator Dashboard, all of which are
   already role-gated pages).
3. Confirm deleting a post as an Owner/Administrator (via the same "⋯
   Delete" control, which is also shown to Administrators/Owners on
   any post) removes it for every visitor, not just the moderator's own
   browser.

## 8. Delete User / Delete Mentor Application — quick functional test

1. As the Owner, attempt to delete your own account from the Users tab
   — confirm you see "You cannot delete the account you are currently
   using." and no request is sent.
2. Create a second test Owner account (via the Administrators panel,
   promote an Administrator to Owner — see `AUTH-SECURITY-SETUP.md` for
   how ownership transfer works), then confirm the *original* Owner
   account can now be deleted (since a second active Owner exists), but
   confirm deleting the *only remaining* active Owner is still blocked.
3. Delete a test Explorer account entirely; confirm they can no longer
   log in afterward.
4. Submit a test mentor application, then delete it as the Owner;
   confirm the applicant's account and (if they were approved) Mentor
   role are unaffected.
