# WRLD Website V20.6.2 — Cache/State Testing

This document distinguishes four different kinds of verification performed for this release, since they carry different weight:

- **Static code validation** — reading the code and its diff against the V20.6.1 baseline.
- **Local/simulated logic testing** — actually *executing* the real, unmodified `app.js`/`auth.js` source in a Node.js sandbox against a scripted fake Supabase server, driving the exact account-switching sequences from the required test list.
- **Connected Supabase testing** — exercising the real, connected WRLD Supabase project.
- **Hosted browser testing** — exercising the real, deployed site in Safari/Chrome desktop/mobile.

**This environment has no connected Supabase project and no browser/device access**, so the last two categories were **not performed** and are not claimed. This is stated plainly rather than implied otherwise — see "Testing limitations" below.

---

## 1. Static code validation

- `node --check` passed with no syntax errors on `app.js`, `auth.js`, `supabase-client.js`, and every modified inline `<script>` block (`assessment.html`, `signup.html`, `login.html`, `email-verified.html`), extracted and checked individually.
- Every reference to the old constants (`STORE_KEY`, `STATE_OWNER_KEY`, `VOLUNTEER_LOG_KEY`, the bare `ASSESS_KEY`) was searched for across the entire project (`.js` and `.html`) and confirmed gone — nothing outside `app.js`/`assessment.html` ever referenced them directly, so no other file needed to change.
- A full recursive `diff -rq` between the attached V20.6.1 baseline and the finished V20.6.2 project confirmed **exactly** 34 changed files: `app.js`, `auth.js`, `supabase-client.js`, `assessment.html`, `signup.html`, `login.html`, `email-verified.html`, 26 other HTML pages (cache-busting only — confirmed by line-level diff to be *only* their `<script>` version-query changes, nothing else), plus the two new documentation files. No image, CSS, Supabase migration, or Edge Function differs at all.
- Line-level diffs of every changed file were read in full (not just file names) to confirm each change directly supports this exact repair — see `CHANGES-V20.6.2.md`'s changed-file inventory.

## 2. Local/simulated logic testing

Because this environment cannot run a real browser or a real Supabase project, the actual, unmodified `app.js` and `auth.js` source files were loaded into a Node.js `vm` sandbox (a real, unmodified JS engine executing the real project code — not a rewritten test double of the logic) with:

- A minimal `localStorage` polyfill that persists across simulated "page navigations" within one test (matching the real-browser property that `localStorage` survives navigation within the same origin).
- A fake Supabase client implementing exactly the query shapes `app.js` uses (`.from(table).select().eq().maybeSingle()`, `.upsert()`, `.order()`, `.delete().eq().in()`) against an in-memory table store, so `pullLearnerStateFromSupabase()`/`pullVolunteerEntriesFromSupabase()`/`syncLearnerStateToSupabase()`/`syncVolunteerEntriesToSupabase()` run for real, unmodified.
- A `simulateAuthResolve(user, db)` helper that reproduces exactly what `supabase-client.js`'s `wrldRefreshSessionCache()` does on a real sign-in/sign-out/session-restore: stamp the active-account pointer, then pull learner state and volunteer entries.
- A fresh JS execution context per simulated "page load" (mirroring a real full-page navigation resetting in-memory JS state) while reusing the *same* `localStorage` object (mirroring a real browser's persistent storage across navigations on one browser).

## 3. Connected Supabase testing

**Not performed.** This environment has no connected Supabase project for this release (V20.6.1's document referenced a connected `WRLD-production` project during its own investigation; that connection is not available here). No `learner_state`/`volunteer_entries`/`profiles` rows were read, written, or modified as part of this release — the fix required no schema, RLS, trigger, or Edge Function change, so there was nothing to verify against a live database beyond confirming (by reading the code) that both tables' existing RLS/user-scoping continues to apply exactly as before.

## 4. Hosted browser testing

**Not performed.** This environment cannot open Safari, Chrome, or any other browser, desktop or mobile, against a hosted or local build of this site. The required cross-account scenarios (Tests 1–8 in the project brief) were instead exercised through the Node.js simulation described in section 2, which runs the real, unmodified application logic rather than a description of it — but this is not a substitute for opening the actual deployed site in the four required browser/device combinations (Safari desktop, Safari mobile, Chrome desktop, Chrome mobile) before considering this shipped. That remains a manual step for whoever deploys this release.

## Testing limitations (stated plainly)

- No real browser, real device, or real Supabase project was available in this environment. Every claim above is scoped to what was actually verified (static analysis + a real-code Node.js simulation), not extrapolated to "this was tested live."
- The simulation's fake Supabase client implements only the specific query patterns `app.js` actually calls — it is not a general-purpose Supabase emulator, and does not exercise real network latency, RLS policy evaluation, or Supabase Auth's actual token/session mechanics (`persistSession`, `autoRefreshToken`, `onAuthStateChange` timing). The `wrldSetActiveStateOwner()`/pointer design was specifically chosen to be safe under realistic timing (see `CHANGES-V20.6.2.md`'s "Timing safety" section), but its behavior under real network conditions, real Safari/Chrome storage-partitioning quirks, or real multi-tab `onAuthStateChange` races has not been observed directly.
- **Before considering this release complete, the required manual test list should be run against a real deployment**: User A completes onboarding → logs out → brand-new User B signs up → B gets fresh onboarding and never sees A's progress; B logs out → A logs back in → A's original progress returns; a browser with old shared cache signs up a new account → stale data is rejected — all four browser/device combinations, all without manually clearing browser history between steps, exactly as the release requires.
- A one-time Cloudflare cache purge is recommended immediately after deploying this release (standard practice for any static-file update, not specific to this bug), even though the cache-busted `?v=20.6.2` script references are the actual, permanent fix for browsers/CDNs serving a stale copy of `app.js`/`auth.js`/`supabase-client.js` going forward.

## No database migration or Edge Function

Stated explicitly: this release requires **no** Supabase migration, RLS change, trigger change, or Edge Function deployment. `learner_state` and `volunteer_entries` were already correctly scoped by `user_id` server-side; the bug and its fix are entirely in client-side `localStorage` key namespacing and routing-inference logic. Deploying this release is only a matter of copying the updated static files to hosting.
