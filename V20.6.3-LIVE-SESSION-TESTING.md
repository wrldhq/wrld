# WRLD V20.6.3 — Live Session / JWT Timing Testing

## What kind of testing this document reports

Four distinct categories, called out explicitly per test below — **do not read any result here as live/hosted verification unless it's labeled that way**:

1. **Static validation** — reading the code, `node --check` syntax validation, and a full recursive `diff` against the V20.6.2 baseline to confirm the changed-file inventory is exactly what `CHANGES-V20.6.3.md` claims.
2. **Local simulation** — a Node.js harness (`local-simulation/simulate.js`, `local-simulation/simulate_auth.js`, included in this ZIP) that loads the **real, unmodified** `supabase-client.js` and `auth.js` files inside a sandboxed VM with a scripted fake Supabase client (configurable to fail with `401 JWT issued in future`, `PGRST116` no-rows, permanent errors, etc. on a per-attempt basis) and a fake `localStorage`. This exercises the actual retry/ownership/state-machine code, not a re-implementation of it — but it is **not** a real Supabase project, a real browser, or real network timing.
3. **Connected Supabase testing** — running this code against a real Supabase project (a real `signUp()`, a real `profiles` table, real RLS, real network latency). **Not performed in this session** — no live Supabase project credentials or environment were available. This is what would be needed to reproduce the actual `401 JWT issued in future` response from a real PostgREST instance and confirm the retry recovers from it in production conditions.
4. **Hosted browser testing** — opening the deployed site in Safari/Chrome/desktop/mobile and clicking through the flow by hand. **Not performed in this session** — no hosted environment or browser automation against the live site was available.

Everything below is (1) and (2). Anything claiming (3) or (4) would be a claim this session cannot honestly make, and none is made.

## Root-cause reproduction (local simulation)

`local-simulation/simulate.js` scripts a fake `profiles` table to return exactly `{ error: { message: 'JWT issued in future', status: 401 } }` on the first call for a brand-new session, then succeed on the second — reproducing the reported live symptom's data shape without a real Supabase project. Against the **unmodified V20.6.2** `supabase-client.js`/`auth.js` (kept in `baseline/` alongside this build for comparison), this exact scenario makes `wrldBuildUserFromCache()` return `null`, `isAuthenticated()` return `false`, and `requireAuth()` redirect to `login.html` — reproducing the bug. Against the **V20.6.3** files, the same scripted scenario resolves to `wrldGetAuthState() === 'authenticated'` throughout, `wrldGetProfileState()` ending at `'loaded'`, and `requireAuth()` returning `true` with no redirect. This is the core of the fix, demonstrated against the real code paths.

## Required tests

### Test 1 — New signup with immediate session
**Category: local simulation.** `simulate.js` Scenario A drives the real dual-call race this codebase actually has during signup (the `onAuthStateChange` listener's own `SIGNED_IN`-triggered call **and** `auth.js`'s explicit `await wrldRefreshSessionCache(data.session)` call, both firing for the same brand-new session — confirmed via diagnostic logs that this race is real, not hypothetical) with a scripted first-attempt `401 JWT issued in future` followed by success. Result: `wrldGetAuthState()` stays `'authenticated'` throughout, `wrldGetProfileState()` ends `'loaded'`, exactly one profile fetch is made per session (de-duplicated), no redirect. `simulate_auth.js` Scenario 3 additionally confirms `requireAuth()` returns `true` and `getCurrentUser()` reflects the loaded profile once this resolves — i.e., the path to the Adulting Readiness Assessment (unchanged in this release) is reachable. **Not performed as connected/hosted**: no real signup against a live Supabase project or a real browser click-through.

### Test 2 — First profile request fails temporarily
**Category: local simulation.** `simulate.js` Scenario A (transient failure, recovers) and Scenario C (`PGRST116` no-rows-yet, recovers) both pass: the user "remains in onboarding" is modeled as `wrldGetAuthState()` never leaving `'authenticated'` and `requireAuth()` (`simulate_auth.js` Scenario 1) never navigating to `login.html`, even when every one of the 3 bounded attempts fails (Scenario B, `simulate.js`) — `wrldGetAuthState()` stays `'authenticated'`, only `wrldGetProfileState()` moves to `'permanent_error'`, and `requireAuth()` still returns `true` (`simulate_auth.js` Scenario 1a/1b). **Not performed as connected/hosted.**

### Test 3 — Returning user
**Category: local simulation + static review.** `simulate_auth.js` Scenario 3 confirms a normal, successful profile load leaves `requireAuth()` returning `true` with `getCurrentUser()` populated — the unchanged `postAuthDestination(next, 'login')` routing (verified unchanged by the full-project diff below) still sends a returning user straight to their role dashboard, never through onboarding. **Not performed as connected/hosted.**

### Test 4 — Same-browser account switch
**Category: local simulation.** `simulate.js` Scenario E: Account A's session resolves and its profile loads; A logs out (`wrldRefreshSessionCache(null)` → `wrldGetAuthState() === 'unauthenticated'`, profile cache cleared); Account B's session then resolves and its profile fetch is confirmed to query **only** `user-BBBBBB`, never reusing or returning Account A's cached row. **Not performed as connected/hosted** (a real two-account, same-browser click-through was not run).

### Test 5 — Welcome page with valid session
**Category: local simulation.** Covered by Test 1/2's `requireAuth()` results directly on the (real) `welcome.html`-equivalent guard logic — onboarding remains active for a valid, confirmed session regardless of profile-fetch outcome. **Not performed as connected/hosted** (an actual `welcome.html` page load in a browser was not exercised — see the `getState()` stub note below).

### Test 6 — Welcome page genuinely logged out
**Category: local simulation.** `simulate_auth.js` Scenario 2: with no session at all, `requireAuth()` returns `false` and navigates to `login.html?next=welcome.html` — confirming this release did **not** regress the genuine logged-out case while fixing the false-positive one.

### Test 7 — Slow session restoration
**Category: static review.** `window.wrldAuthReady` (unchanged bootstrap pattern from V20.6.2/V20.5) is still awaited before `requireAuth()` runs on every gated page, including `welcome.html`. The bounded retry adds at most a few seconds (3 attempts × up to 550ms×attempt backoff + one `refreshSession()` round trip) to how long that promise takes to resolve in the failure case — it does not change the "await before anything renders" pattern that prevents a premature redirect during slow restoration. **Not performed as connected/hosted** (no real slow-network condition was simulated against a live project).

### Test 8 — Profile row delayed
**Category: local simulation.** `simulate.js` Scenario C — a `PGRST116` "0 rows" response (profile-creation-trigger race) followed by success within the bounded retry window resolves to `wrldGetProfileState() === 'loaded'`. **Not performed as connected/hosted** (the real `handle_new_user()` trigger's actual timing was not exercised against a live database).

### Test 9 — Multiple devices (Safari desktop/mobile, Chrome desktop/mobile, Windows browser)
**Category: not performed.** This requires hosted/connected testing across real devices and was out of reach in this session (no browser automation or device farm access). What this release *can* say with confidence: the reported bug reproduced identically across a Windows laptop, a MacBook, and an iPhone, which is itself evidence the root cause is a server/client timing race common to all of them (the JWT `iat` vs. PostgREST validation window), not a per-device clock setting — and the fix (bounded retry + session-state/profile-state separation) does not depend on any device- or browser-specific behavior, so there is no reason to expect it to behave differently per platform. This is a reasoned expectation, not a verified one.

## Simulation harness limitation, stated plainly

The local simulation stubs `getState()` (which lives in the unchanged `app.js`, not loaded in the harness) to always report "no assessment yet" so `requireAuth()`'s onboarding-redirect branch can be exercised in isolation. It does not load `app.js`, `orbit.js`, `data.js`, or render any actual DOM/CSS — it is a targeted logic test of the auth/profile state machine and routing decisions, not a rendering or integration test. Actual page rendering (`welcome.html`'s greeting vs. recovery-message DOM swap) was verified by static code review and a Node.js syntax check (`node --check`) of the extracted inline script, not by rendering it in a browser.
